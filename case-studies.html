    STUDS Building a Design System People Actually Wanted to Use

    Overview

    When most people hear the term design system, they think of component libraries, style guides, design tokens, or documentation.

    STUDS certainly included all of those things. But that isn't why it existed.

    At its core, STUDS was an effort to help a seventy-year-old company present a more consistent experience across dozens of independent software applications. It became a shared language between designers and developers, a foundation for accessibility, and ultimately an exercise in organizational change as much as front-end architecture.

    My role was to help bridge the gap between design and engineering by translating design decisions into practical implementation while ensuring the system remained flexible enough for teams with very different technologies and workflows.

    The Challenge

    Simpson Strong-Tie is known worldwide for manufacturing structural connectors, fasteners, anchors, and building products. Over decades, the company also developed a broad portfolio of software used by architects, structural engineers, contractors, builders, and homeowners.

    Like many mature organizations, those applications evolved independently. Different products were built by different teams, different technologies were adopted over time. Some applications were native desktop software, others were built using C#, React, Angular, or other web technologies.

    Each solved its own business problem well, but collectively they looked and felt like software from different companies.

    At the same time, expectations around software were changing. Users no longer expected applications to exist only on desktop Windows computers. Tablets were becoming common on construction sites, and responsive web applications were increasingly replacing traditional desktop software.

    The company recognized that modernizing individual products wasn't enough. The experience itself needed to become more consistent.

    Building a Shared Language

    One of the first realizations while creating STUDS was that consistency doesn't begin with components, it begins with conversation.

    Before writing a single component, designers, developers, and stakeholders spent considerable time agreeing on how software should look, behave, and communicate: typography, spacing, corner radius, color, interaction patterns, accessibility, and responsive behavior.

    Those conversations became the real foundation of the design system.

    Instead of treating design and development as separate disciplines, STUDS intentionally created a common vocabulary between them.

    Design tokens inside Figma matched the CSS variables and design tokens used by developers. When a designer specified a color or spacing value, developers could immediately recognize the corresponding implementation without translating between different naming systems.

    That shared language reduced ambiguity, improved communication, and made implementation significantly more predictable.

    Simplicity Takes Work

    One of the earliest discussions centered around color. Initially, the design system included multiple primary color palettes, each representing a family of related applications. Applications intended for architects used one visual identity. Software designed for structural engineers used another. Consumer-facing applications for builders and homeowners introduced additional palettes. The intention was to help users recognize which family of applications they were working with.

    The idea was thoughtful, but over time we questioned whether those distinctions actually helped users accomplish their work. For many people, the color differences didn't communicate meaningful information. Instead, they introduced another visual system that users first had to learn before it became useful.

    As the design system matured, we simplified the palette and centered it around the company's primary brand colors.

    That wasn't simply a branding decision, it was a usability decision. Like many aspects of STUDS, the goal wasn't to add more visual language, it was to remove unnecessary complexity.

    Designing for Behavior

    Another important discussion centered around responsive design. Many design tools naturally encourage designers to think in terms of desktop, tablet, and mobile layouts.

    My experience had taught me to approach responsive design differently.

    Rather than asking how a page should change at specific breakpoints, I preferred asking how each individual component should behave as available space changed. At the time, technologies like CSS Container Queries didn't yet exist as a browser baseline, making that vision difficult to implement directly.

    Even so, the conversation shifted. Instead of designing pages, we designed behaviors. This way of thinking influenced many later decisions within STUDS and eventually became one of the ideas that shaped my own front-end methodology.

    One Design System, Multiple Paths

    One of the assumptions we made early in the project was that developers would consume STUDS through CSS. That seemed natural to me because CSS has always been one of my strongest technical disciplines.

    What surprised me was discovering how many application developers rarely wanted to write CSS directly. Many preferred working entirely through framework components, while others were already heavily invested in Telerik's component library.

    Rather than asking every team to change how they worked, we adapted the design system to fit their existing workflows.

    Teams comfortable writing CSS could simply include the standalone STUDS stylesheet, gaining access to shared colors, typography, spacing, tokens, themes, and component styling.

    Teams building applications with supported frameworks could instead use component libraries that embedded STUDS automatically, allowing them to build interfaces without writing CSS themselves.

    Finally, for teams already committed to Telerik, I translated the design language into a Telerik theme that could be integrated directly into their existing applications.

    The underlying design language remained identical, only the implementation changed. That became one of the most important lessons from the project.

    Consistency should be the goal. Implementation can take many paths.

    The success of a design system isn't measured by whether everyone writes code the same way, it's measured by whether users experience software that feels coherent, regardless of how it was built.

    Accessibility as a Foundation

    Accessibility was never treated as an optional enhancement, it was part of the system from the very beginning.

    Instead of restricting designers to a limited set of "accessible colors," STUDS provided accessible alternatives through design tokens, themes, and modern CSS.

    A designer could work naturally using the design language they needed while the system automatically supported higher-contrast themes for users who requested them through their operating system or browser preferences.

    The same philosophy extended beyond color.

    Spacing, typography, motion preferences, and scalable sizing were all incorporated into the system itself rather than handled as individual exceptions.

    The goal wasn't to bolt accessibility onto existing components, it was to make accessibility part of the architecture.

    Lessons Learned

    Looking back, the most valuable part of STUDS wasn't the component library, it wasn't the design tokens, and it wasn't even the documentation. The greatest success was creating shared understanding.

    Designers and developers began speaking the same language. Implementation decisions became easier because the underlying design decisions had already been discussed. Different teams continued using different technologies, yet users experienced a more consistent product.

    Perhaps the biggest lesson I took away was that successful architecture isn't about enforcing one implementation, but it is about creating shared principles that allow many implementations to arrive at the same destination.

    STUDS reinforced something I've come to believe throughout my career:

    • Technology changes.
    • Frameworks change.
    • Design trends change.

    But reducing unnecessary complexity while helping people work together more effectively… that never goes out of style.

    iSeq 100 Making Complex Science Easier to Use

    The Challenge

    When I joined Illumina, much of its software had been designed for highly experienced scientists working with sophisticated sequencing equipment.

    The iSeq 100 was different.

    It was a smaller, more approachable sequencing system intended to bring next-generation sequencing into environments that might not have dedicated sequencing experts.

    That changed the design problem. A lab technician operating an iSeq 100 shouldn't need a PhD in genetics to understand what the software was asking them to do.

    My job was to help make an extraordinarily complex scientific process feel understandable.

    Designing the Workflow

    I owned the user-facing workflow for the iSeq 100 control software, including the interaction design, interface design, animations, and transitions that guided users through a sequencing run. This required understanding much more than the screen in front of me.

    The software had to coordinate with physical hardware, backend processes, consumables, system states, and the expectations of people using the instrument.

    I worked across front-end and backend software teams, hardware engineers, marketing, UX, and other stakeholders to understand those dependencies and translate them into a coherent user experience.

    In many ways, my role was to connect the dots.

    Prototyping the Experience

    Rather than relying entirely on static mockups, I built functional prototypes that allowed us to experience interactions and workflows before they were committed to production.

    This mattered because interaction problems can be difficult to see in a sequence of static screens. A workflow might look perfectly reasonable in a design file and still feel confusing once someone actually tries to move through it.

    Functional prototypes gave us a way to test assumptions, incorporate findings from user testing, demonstrate animations and transitions, and identify problems earlier, when they were still relatively inexpensive to change.

    Designing for Someone Like Me

    One unusual advantage I brought to the project was that I wasn't a geneticist. I had to learn what the terminology meant and why each step existed.

    Rather than treating that as a weakness, I found it useful.

    If I couldn't understand an instruction, there was a reasonable chance that someone operating the instrument for the first time might struggle with it too.

    That made me particularly sensitive to terminology, hierarchy, feedback, and the amount of information we expected users to understand at each step.

    The goal wasn't to remove the science, it was to reveal only as much complexity as the user needed at that moment.

    Seeing It Become Real

    One of the proudest moments of my career was seeing the interface running on the actual production instrument as the iSeq 100 prepared to ship.

    For months, the experience had existed as sketches, prototypes, design files, discussions, animations, and code. Then suddenly it was part of a physical product.

    Something we had been working on, debating on, and user testing was now going into laboratories around the world.

    The interaction and interface work I contributed to the iSeq 100 ultimately resulted in three U.S. design patents covering aspects of its interface and workflow:

    • US D873281 S
    • US D895640 S
    • US D932500 S

    But the patents aren't what I remember most about the project. I remember the craftsmanship.

    The iSeq 100 gave me an opportunity to concentrate deeply on one experience, refining interactions, questioning terminology, testing workflows, and making something technically complex feel progressively simpler.

    It remains one of my favorite projects because it demonstrated something I've believed throughout my career:

    Complexity isn't necessarily the problem. Confusion is.

    PuppySpot Building a Modular Page Architecture for Composable Content

    The Problem

    I joined PuppySpot after a major design overhaul. The new design worked, but it introduced a number of difficult interaction and responsive-layout problems. Pages were being treated largely as fixed compositions, with layouts changing at predefined desktop, tablet, and mobile breakpoints.

    That approach made each page another design problem.

    I wanted to make the components themselves solve more of those problems.

    The Solution

    Rather than designing every page independently, I began developing a library of reusable content modules.

    A page could be assembled from combinations such as:

    • Hero A
    • Feature Grid C
    • Testimonials B

    Instead of asking designers and developers to repeatedly solve the same layout problems, each module defined its own structure and responsive behavior.

    The page became a composition of known pieces.

    Ten Modules, Fourteen Layouts, Fourty-Two Responsive Variations

    The system eventually contained 10 core modules with multiple variations, producing roughly fourteen usable layout configurations, not including the responsive variations.

    The important part wasn't the number as much as what those combinations allowed the team to do:

    • Marketing could create pages from a vocabulary of established patterns rather than beginning with a blank canvas.
    • Designers could concentrate on choosing the right composition.
    • Developers could work with known structures instead of receiving an entirely new layout with every project.

    And because responsive behavior belonged to the modules themselves, pages became much less dependent on rigid device-specific layouts.

    Reference Implementations

    I built the modules as functional HTML, CSS, JavaScript, and jQuery prototypes, not just as visual demonstrations, but as reference implementations.

    Developers could inspect exactly how the component behaved, how it responded as space changed, and how interactions were intended to work. This reduced the gap between design intent and engineering implementation.

    A Shared Language

    One of the unexpected benefits was communication. Instead of saying:

    "Put a large image here, then this kind of text block, followed by the three-column thing we used on that other page..."

    people could say:

    "Hero A, Feature Grid C, Testimonials B."

    Everyone knew what that meant. The module library had become a shared vocabulary between design, marketing, stakeholders, and engineering.

    Guidelines, Not Restrictions

    The system wasn't intended to eliminate one-off design. Sometimes a page genuinely needed something unique. Instead, the goal was simply to stop solving already-solved problems.

    Reusable modules provided a strong default while leaving room for deliberately crafted experiences when they were justified.

    What I Learned

    This project changed how I thought about responsive design. Responsiveness shouldn't primarily belong to the page, it should belong to the component.

    A component should understand how to adapt to the space available to it, regardless of where it appears.

    Browser technology would eventually make that idea much easier to implement through features such as container queries, but the underlying idea was already there:

    Build adaptable pieces, then compose the experience from them.

    Business.com Bridging Design and Engineering During the Responsive Web Transition

    Modernizing the Front End

    When I joined Business.com, I was the primary front-end and UX specialist on a team made up largely of backend engineers.

    My role eventually covered the entire path from interface concept to production code. I created wireframes, worked through interaction and visual design, and then implemented those designs using PHP, HTML, CSS/Sass, JavaScript, and jQuery.

    It was a period when the web itself was changing quickly and responsive design was becoming the expectation rather than the exception. CSS tooling was evolving, and websites were moving away from rigid desktop-oriented layouts.

    Much of my work involved helping Business.com make that transition.

    Before Sass

    The existing front end had accumulated years of CSS, including an outdated CSS framework. Maintaining it was difficult, and seemingly small visual changes could require hunting through large stylesheets to understand what depended on what.

    When I started at Business.com, Sass still wasn't robust enough for what we needed, so I developed a custom solution using PHP to parse styles, variables, and functions and output CSS. This sustained us for a while, but I kept my eye on the progress of Sass as a tool to use in out build process.

    Once it became a solid choice, I helped move the front end toward Sass and a more structured approach to reusable styles. The reason was for performance as much as for maintainability of styles.

    While PHP and other server-side rendering technologies are still preferable, in my mind, to front-end heavy applications, Sass allowed us to compile the CSS before going to production. On our already heavy pages, every little bit helped to decrease load times and increase overall user experience.

    Responsive Design

    One of the most important changes was moving away from treating desktop, tablet, and mobile as separate designs. I worked closely with the lead designer, translating designs into responsive interfaces and making decisions about what should happen in the spaces between the supplied compositions.

    Eventually, something interesting happened. The designer stopped creating separate tablet and mobile comps for me.

    He told my manager he didn't need to. He would give me the desktop design and trusted me to understand how it should adapt. He jokingly referred to what happened between desktop and mobile as JP doing his "magic."

    There wasn't any magic involved. I had simply developed a strong understanding of how layouts should flow and how components should respond as available space changed. That trust remains one of my favorite compliments from my career.

    Translating Design

    A large part of my job was translating between disciplines.

    • Designers shouldn't have to understand every browser limitation to explore an idea.
    • Backend developers shouldn't have to become interaction designers to implement it.

    I could work between those worlds, understanding the design intent, recognizing the technical constraints, and finding an implementation that respected both.

    That role would become increasingly important throughout the rest of my career.

    The CSS Guy

    Because most of the engineering team specialized in backend development, I naturally became the person people came to when something involved CSS, responsive behavior, or unusual front-end interactions.

    I enjoyed that position because it wasn't just about fixing styles. It gave me opportunities to explain why something behaved the way it did and to help other developers become more comfortable working in the browser.

    What I Learned

    Business.com was where responsive design stopped feeling like a technique and started becoming a way of thinking. The browser isn't a collection of fixed canvases, it's a continuously changing environment.

    Once I understood that, I stopped thinking primarily about how pages should look at particular widths and started thinking about how interfaces should behave everywhere between them.

    That idea would follow me into PuppySpot, STUDS, and much of my later work.

    San Diego State University Field Stations Program Designing Clear Information for High-Stress Situations

    The Context

    I worked with the San Diego State University Field Stations Program during a period when my role expanded well beyond web development.

    The program operated four field stations, each with its own identity and communication needs.

    I helped create a more unified visual presence across those locations, including websites, logos, brochures, letterhead, photography, and other materials. I also brought the program's web presence into compliance with Section 508 accessibility requirements.

    But one project in particular changed how I thought about information design.

    Fire safety.

    Designing for an Emergency

    Wildfire is a very real concern. Not just for Southern California in general, but also for the biological field stations.

    The Field Stations Program needed a website that could communicate changing fire conditions, threat levels, evacuation information, and downloadable safety materials.

    This wasn't a site people would necessarily browse casually. Sometimes, visitors might arrive because something was wrong and they needed to know what to do.

    That changed the design decisions.

    During an emergency, people don't need clever navigation. They don't need decoration. What they do need is to know:

    • What's happening?
    • How serious is it?
    • What am I supposed to do?
    • Where do I go?

    The interface needed to make those answers obvious.

    The system I created was able to react on-the-fly to real-time danger levels. Under low to moderate fire danger levels, a user would get the full website, with planning information, activity booklets for children, and other educational materials.

    But during a fire emergency, the site automatically switched over to an extremely low-data version that could be accessed on cell phones, giving just the needed information such as escape routes, evactuation orders, and emergency services.

    Clarity Before Decoration

    The project reinforced something that would influence much of my later UX work: the more stressful the situation, the less cognitive effort an interface should require.

    Hierarchy, language, color, and accessibility all matter.

    Information needs to be understandable quickly, without requiring users to interpret the design before they can interpret the message.

    That lesson would eventually apply in very different environments later in my career, from scientific instruments to design systems, but the underlying principle remains the same.

    Good interface design isn't about making information look interesting. It's about making the next decision easier.

    CSUPERB Turning a Manual Academic Workflow into Software

    The Problem

    The California State University Program for Education and Research in Biotechnology (CSUPERB) managed grant proposals, conference abstracts, peer review, and related academic workflows across the California State University system.

    Much of that work depended on manual administrative processes: submissions had to be collected, reviewers assigned, materials organized, decisions tracked, and conference information eventually had to be assembled into printed materials.

    The challenge wasn't simply putting forms online, it was about understanding the entire workflow.

    Building the System

    I was the sole developer on the project. I designed and built a web-based system that supported three primary roles:

    • applicants and submitters
    • reviewers
    • administrators

    The system included authentication, database-driven submissions, administrative tools, reviewer workflows, and the underlying logic needed to move information through the process.

    I handled the database, PHP development, HTML, CSS, authentication, and administration interfaces.

    Today we'd probably call it a full-stack application. But at the time, I just thought of it as solving a problem.

    Automating the Work Around the Work

    One of the most useful parts of the system had little to do with the submission form itself. Once the information was structured in a database, we could reuse it.

    Data that previously had to be manually collected and reformatted for conference materials could now be generated automatically. A process that had consumed an enormous amount of administrative time could happen in minutes.

    That was the part I found most satisfying. The best automation isn't necessarily the part users see. Sometimes it's the workload that simply disappears.

    What I Learned

    CSUPERB taught me to look beyond the immediate feature I was being asked to build.

    Putting a submission form online solved one problem. But understanding where that information came from, who needed it next, and what ultimately happened to it revealed opportunities to improve the entire process.

    That became an important lesson for me: Don’t just automate the task. Understand the workflow around it.

    Sometimes the greatest improvement isn’t making one step faster. It’s recognizing that an entire step no longer needs to exist.

    Professional Sound & Music Designing Software for a Business That Didn't Fit the Software

    The Problem

    Before I worked professionally in web development, I spent years in music retail selling professional audio equipment, synthesizers, and digital recording systems.

    The store had the same problem many small businesses had at the time: available software didn't really match how the business worked.

    Sales were only part of the operation. We also needed to track inventory, customer information, repairs, equipment histories, and the movement of gear through the shop.

    So I started building our own tools.

    Building Around the Workflow

    My first version was built in HyperCard on the Macintosh. We then tried a variety of off-the-shelf applications to handle our needs, but none of them really did what we wanted, and they couldn't handle the unique needs of the business. We kept trying to just "make it work". But again, the software was getting in the way and not helping to solve a problem.

    I then started to build a more capable FileMaker-based system that handled point-of-sale functions along with inventory and repair tracking.

    The important part wasn't the technology. I understood the workflow because I was part of it. I knew what information the salesperson needed. I knew what the repair department needed. I knew what happened when equipment came back months later and someone needed to understand its history.

    Instead of changing the business to fit the software, I changed the software to fit the business.

    What I Learned Before I Knew I Was Learning It

    At the time, I didn't call any of this UX. I wasn't thinking about product design or information architecture. I was simply frustrated by inefficient tools and knew enough about computers to try building something better.

    Looking back, the same pattern appears throughout much of my later career:

    • Understand how people actually work.
    • Find the unnecessary friction.
    • Build something that removes it.

    While the technologies have became much more sophisticated over the years, that pattern never really changed.

    Still Working Ten Years Later

    Years after I'd left the music store and moved on to a career in web development, I learned that the software I'd written was still being used.

    Roughly a decade later, it was still doing its job.

    That has always stuck with me. It wasn't built with a technology anyone would consider modern today. It wasn't built with the expectation that it would become an important piece of software architecture. It was built because people had a problem and the existing tools weren't solving it very well.

    And it lasted.

    That experience helped shape the way I think about technology even now.

    • Newer isn't automatically better.
    • Popular isn't automatically appropriate.
    • Technology used to build something isn't what determines whether it was successful.

    Good software solves the right problem for the people who actually use it.

    Sometimes the best evidence that you made the right decisions is simply that, years later, people are still using it.

    Promotional Broadcast Network Building Experiences That Continued After Release

    The Project

    At Promotional Broadcast Network, I served as Art Director and Lead Programmer on a narrative-driven adventure game for both Mac and Windows.

    The experience was inspired by exploration games such as Myst and Riven.

    It combined 3D environments, animation, storytelling, interaction, and software development into a single entertainment experience.

    I directed a team of four artists and programmers while also contributing directly to modeling, texturing, animation, rendering, programming, camera direction, color, and the overall visual language of the game.

    Our 3D workflow evolved from Strata 3D to LightWave as the project grew.

    Keeping the World Consistent

    A project built by several artists can easily begin to feel like several different worlds. Part of my responsibility as Art Director was maintaining consistency: camera choices, lighting, color palettes, environment design, and interaction.

    Those decisions had to reinforce one another so that the player experienced a single coherent place rather than a collection of independently produced assets.

    An Experience That Could Change

    One of the more unusual technical features was an online update system. Although the primary game shipped on CD-ROM, it could connect online and receive new information. That allowed content to change or become available over time rather than remaining permanently frozen at the moment the disc shipped.

    Today, continuously updated software is ordinary. But at the time, the distinction between packaged software and online experiences was much stronger.

    Building a system that crossed that boundary opened up interesting possibilities for storytelling. The experience didn't necessarily have to end when the software shipped. It also gave us, the artists and developers, a little leeway. While we needed to have assests locked down when the CD was pressed, we still had a couple weeks after that to continue refining and testing before the game went live.

    That was a luxury compared to many of today's continuous-integration pipelines.

    Looking Back

    The tools we used are obviously very different from the ones I use today, but the underlying problems aren't.

    • How do several disciplines contribute to one coherent experience?
    • How do visual design, interaction, technology, and story reinforce each other?
    • How can technology support an idea without becoming the idea itself?

    Those are questions I've continued asking throughout my career.
